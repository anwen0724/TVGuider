# Spec 编写规范

本文规定 TV-Guider 的功能、基础能力或业务流程进入 Coding 前必须完成的 Spec 内容。Spec 用于确认本次开发要实现什么、功能如何工作，以及通过哪些行为场景判断做对了。行为测试方案及适用的效果评估方案写入 2.6 验收标准；文件修改、测试代码、编码步骤、测试命令或交付顺序由 Implementation Plan 安排。

一份 Spec 对应一个边界明确、职责内聚、能够定义验收结果的功能或能力。允许依赖其它模块，但必须明确依赖提供的契约、本份负责的行为及集成验证边界。具有不同结果和验收责任、可以独立演进的能力应考虑拆分；不能仅因接口、类、文件或测试数量不同而机械拆分。相关设置、查询与校验可以共同组成一个完整的管理能力。

## 一、固定结构

每份 Spec 在标题下方列出以下文档信息，不增加一级章节：

```text
状态：讨论中 / 已确认 / 已取代
版本：
最后更新日期：
确认日期：未确认时留空
关联文档：无则写“无”
```

已确认 Spec 的功能语义、契约或范围发生变化时，应记录变化并重新确认；重新确认前，变更部分不得作为实施依据。纯文字整理不需要重新确认。

每份 Spec 只使用以下三个一级章节：

```text
一、本次开发目标
二、开发方案设计与要求
三、设计选型考量
```

“设计选型考量”必须是最后一章。第二章固定按功能定义、数据模型、接口定义、业务规则、状态与流程、验收标准六个设计维度划分。

### 推荐的讨论与确认顺序

文档的固定章节顺序用于组织最终设计，不要求讨论时按目录顺序推进。先确定业务行为，再确定承载这些行为的数据与接口，避免业务规则尚未明确就决定实体数量、库表或字段。

推荐按以下顺序讨论：

1. **目标与功能定义**：确认第一章和 2.1，明确解决什么问题、谁触发、输入和结果是什么，以及功能边界。
2. **业务场景与预期结果**：用具体例子确认正常操作、纠正、撤销、冲突和失败时应发生什么；这些场景作为后续规则与验收的基础。
3. **业务规则（2.4）**：明确优先级、适用范围、冲突处理、禁止行为和边界条件。
4. **状态与流程（2.5）**：明确业务事实如何产生、变化和失效，以及中断、重复执行和失败后的处理。
5. **数据模型（2.2）**：根据已确认的行为确定需要表达的数据、关系和变化，再划分实体、配置、值对象、读取模型和运行对象，定义字段、约束与所有权。涉及持久化时，再明确存储结构及迁移或重建要求。不能把每一类输入、集合或处理步骤直接等同于数据库实体，也不能仅因现有代码或表已存在就默认沿用。
6. **接口定义（2.3）**：明确调用方、操作、输入输出、错误结果和外部依赖约定；讨论前期即应核对已有外部 Contract，避免最终接口与业务边界冲突。
7. **验收标准（2.6）**：将前面确认的场景整理为行为测试方案，写清前置条件、操作和可观察结果，确认正常、边界和异常覆盖，并反查目标、规则、流程、模型与接口是否一致。存在跨 Spec 依赖时，同时明确本份和联合验收的责任与完成条件。

每确认一项重要选型，同步补充第三章中的备选方案、选择理由和代价，不等全部设计结束后再补写。确认内容写入其对应章节，最终章节顺序保持不变。

上述顺序允许根据依赖关系反复核对和修订，不是一次性瀑布流程。后续讨论若改变已确认的产品行为或范围，须明确指出变化并重新确认；不改变已确认含义的文字整理无需重复确认。尚未确认的内容应明确标记为待讨论，不提前写成已确定的设计。

## 二、章节内容要求

### 一、本次开发目标

本章说明本次开发最终要达到的效果，必须写明：

- 功能或业务流程名称；
- 要解决的问题；
- 开发完成后用户或系统具备的能力；
- 本次包含的范围；
- 本次明确不包含的内容。

本章只定义目标和范围，不展开具体实现步骤。

### 二、开发方案设计与要求

第二章固定使用以下结构：

```text
## 2.1 功能定义
## 2.2 数据模型
## 2.3 接口定义
## 2.4 业务规则
## 2.5 状态与流程
## 2.6 验收标准
```

存在尚未确认的问题时，可在第二章正文开头列出待确认问题清单；确认完成后必须将结论写入对应设计位置，不以问题清单代替最终设计。

一个功能内部存在多个具体能力点时，在对应设计维度下使用三级及以下章节展开，不再按能力点重复建立一套第二章结构。某个设计维度不适用时，必须明确写明“不涉及”及其原因，不能直接省略。

### 2.1 功能定义

必须写明：

- 触发方；
- 触发条件；
- 功能输入；
- 最终结果；
- 成功与无法完成的定义；
- 能力边界。

### 2.2 数据模型

先说明本功能需要表达的数据及其语义；数据模型不限于数据库实体，也包括配置、值对象、消息、读取模型、运行状态和快照。不得为了满足模板引入无需求依据的表或对象。

**数据定义与约束**

- 涉及的数据类型及其职责；
- 字段、类型、业务含义、可选性、默认值及有效值约束；
- 数据之间的关系、标识及一致性要求；
- 适用的状态、所有权、可变性与快照隔离要求。

**数据变化**

- 读取、新增、修改和删除哪些数据；
- 谁负责创建、修改、保存或释放；
- 变化对既有引用、快照或其它关联数据的影响。

**持久化设计（涉及时）**

- 使用的存储形式及需要保存的数据；
- 使用关系表时，明确新增或复用的表、字段类型、主键和外键、唯一约束、非空约束、默认值、索引及数据一致性约束；
- 使用其它存储形式时，说明相应结构、标识、约束和读写一致性。

**迁移与兼容（涉及时）**

- 是否需要迁移或重建；
- 旧数据如何处理；
- 迁移期间及迁移后的兼容要求。

不涉及持久化或迁移时，简要说明“不涉及”及原因即可，不必逐项填写表、索引和迁移的“不涉及”。不涉及持久化不代表可以省略内存数据、配置或运行对象的语义与变化规则。

Spec 确定需要表达和保存什么数据、适用的约束及功能语义；迁移文件、Schema 文件、Repository 文件等具体修改位置由 Implementation Plan 确定。

### 2.3 接口定义

**对外提供**

- 调用方；
- 接口、方法或操作；
- Input；
- Output；
- 无法完成或发生错误时的结果。

**外部依赖**

- 依赖的外部能力；
- 调用的方法或操作；
- Input；
- Output；
- 依赖失败时的处理方式。

这里定义的是调用约定，不提前规定文件名、类名或内部代码组织，除非它们本身就是已经确认的架构约束。

### 2.4 业务规则

必须写明：

- 必须满足的规则；
- 禁止发生的情况；
- 边界情况及其处理结果；
- 多条规则冲突时的优先级。

业务规则必须能够转化为明确判断。不得使用未定义的“合理”“必要时”“适当”“尽量”“相关”“重复”等表达；确需使用时，必须同时给出可以执行和验证的判定条件。

### 2.5 状态与流程

**状态变化**

- 初始状态；
- 允许发生的状态转换；
- 每次转换的条件和结果；
- 不允许发生的转换。

**主流程**

- 从触发到产生最终结果的完整步骤；
- 每一步读取、判断或改变的业务事实。

**异常流程**

- 主要失败情况；
- 中断、重复执行或部分完成等适用场景；
- 每种情况产生的明确结果及后续处理。

功能不存在状态变化时明确写明“不涉及状态转换”，但仍需说明主流程和主要异常流程。

### 2.6 验收标准

功能行为的验收标准以行为测试场景表达，构成本次功能的行为测试方案；涉及检索、排序或模型生成质量时，还应按下文要求补充效果评估方案。行为场景应覆盖已确认的正常场景、关键边界和主要异常情况，并写清前置条件、操作及可观察的预期结果：

```text
场景名称：
给定：
当：
那么：
```

可使用段落或表格；复杂功能可按能力分组并为场景设置稳定编号，供实施任务引用。不规定统一的用例数量，数量由行为差异决定；一个场景可以展开成多个测试，验收项、测试函数、实施任务和提交不要求一一对应。

#### 行为测试要求

- 测试方案验证调用方或系统边界可观察到的行为、业务规则和契约，不断言无关的内部容器、私有方法或文件组织。
- 场景应能判断功能是否按 Spec 完成，不能只写“功能正常”“正确处理”或“符合预期”。
- 场景预期必须与规则、接口、数据模型和流程一致，不能由测试方案自行增加或改变功能语义。
- 功能语义及其行为测试方案在进入实施前确认。原型或测试暴露新的行为取舍时，先更新并确认对应设计，再调整验收场景。
- 不在测试方案中标注行为来自参考项目还是本项目调整；来源和取舍写入第三章。
- 本节不安排测试文件、测试代码、测试替身、运行命令或编码顺序；它们属于 Implementation Plan。

#### 效果评估要求

涉及检索、排序或模型生成质量时，除功能行为测试外，还应定义效果评估方案，包括评估数据及其版本、预期结果或标注依据、指标与计算方式、通过标准，以及影响结果的模型、数据和配置记录要求。存在随机性时，应说明重复评估及结果汇总方式。

功能测试通过不等于效果评估通过；检索效果通过不等于最终修复效果通过。用于调参与最终验收的数据应明确区分。

Spec 定义评估规则和通过标准；评估脚本、执行命令和任务安排由 Implementation Plan 确定。具体指标及门槛在对应 Spec 中确认，本规范不规定统一数值。

#### 本份验收与联合验收

存在跨模块或跨 Spec 依赖时，必须区分本份能够证明的结果与组合后才能验证的行为。联合验收场景应明确：

- 本份已承担和能够验证的行为；
- 依赖的模块或 Spec 及其契约；
- 负责实施联合验证的 Spec 或集成任务；
- 联合验证完成前不能宣称成立的结论。

本份核心目标必须由本份实现并验收，不能通过移入“后续联合验收”来宣布完成。联合验收验证的是组合后的行为，不替代本份交付责任。本地、模拟或契约测试通过不能自动等同于集成或真实外部系统验证通过；交付时分别记录已验证结果和待验证边界。

#### 与 Implementation Plan 的对应

Implementation Plan 开头列出验收项与实施任务的对应关系，引用本节场景及适用的效果评估要求，不复制另一套预期结果。对确定性的功能行为、业务规则和接口契约，按 Red → Green → Refactor 执行 TDD。检索、排序和模型生成的质量按本节确认的效果评估方案验证；相关的输入校验、结果结构、约束处理和错误处理仍采用行为测试。执行规则遵循 [开发交付基线](DEVELOPMENT_BASELINE.md)。

测试验证可观察行为，不复述内部实现。纯文档及不改变运行行为的机械调整，采用与变更相称的检查。

普通实现细节可在 TDD 中确定，实施计划和测试代码不能补充或改变未经确认的功能行为。

### 三、设计选型考量

本章记录本次功能设计为什么这样确定，必须包括：

- 设计时考虑的主要因素；
- 考虑过的可行方案；
- 最终选择及其理由；
- 未采用其他方案的原因；
- 当前选择承担的限制或代价。

引用参考实现或外部资料时，区分已核实的事实、推断和本项目主动选择的行为；对影响功能语义的采用或调整说明依据、理由和代价。不要把“参考某项目”当作全部行为一致的证明。这些说明保留在设计选型中，不进入行为测试方案。

本章只记录影响功能语义、长期职责或重要技术方向的选择，不记录普通编码细节。

## 三、Coding Ready 检查

开始编写正式 Implementation Plan 和功能代码前，必须确认：

- [ ] 开发目标和范围已经明确；
- [ ] 功能输入、结果和能力边界已经明确；
- [ ] 数据类型、字段约束、关系、所有权及变化规则已经明确，或者确认不涉及；
- [ ] 持久化结构、约束、迁移及兼容要求已经明确，或者确认不涉及；
- [ ] 对外接口和外部依赖已经明确；
- [ ] 核心业务规则、禁止情况和边界情况已经明确；
- [ ] 状态变化已经明确，或者确认不涉及；
- [ ] 正常流程和主要异常流程已经明确；
- [ ] 功能语义及 2.6 中的行为测试方案已经确认，正常、关键边界和主要异常场景有可判断的预期；
- [ ] 涉及效果评估时，评估数据要求、指标、通过标准及复现条件已经明确；不涉及时说明原因；
- [ ] 验收场景与业务规则、接口、数据模型和流程一致，不存在需要在编码时决定的关键行为；
- [ ] 跨 Spec 依赖、本份验收和联合验收责任及完成条件已经明确，或者确认不涉及；
- [ ] 关键设计选型及理由已经记录；
- [ ] 不存在需要在编码阶段临时决定的功能行为。

全部满足后，Spec 才达到 Coding Ready。Coding Ready 表示设计足以进入实施，不表示代码已经完成或测试已经通过。

Coding Ready 约束正式功能实施。为解决尚未确定的技术选型，可在讨论阶段开展范围明确的技术验证，并事先说明待验证问题、样本范围和判断依据。技术验证结果应回填设计选型考量；涉及功能语义、契约或范围的结论，确认后才能进入正式实施。原型完成不代表功能验收通过。

Implementation Plan 只能把已确认的设计、验收场景和效果评估要求转换为目标文件结构、TDD 任务和验证安排，不能补充或改变未经确认的功能行为。普通实现细节无需逐项重复确认；影响功能语义、契约或范围的取舍不能留到编码阶段自行决定。
