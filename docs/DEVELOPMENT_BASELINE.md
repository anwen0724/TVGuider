# Development Baseline

## 定位

本文约束 TV-Guider 的 Implementation Plan 中出现的代码、测试、命令和执行步骤，以及后续执行这些计划时的通用工程底线。

本文不规定完整的 Plan 模板；要求文档开头列出验收项与实施任务的对应关系，其余结构按任务需要组织。

本文不定义具体业务规则、架构规则、数据模型、错误模型或模块能力边界。功能语义、对外契约和验收预期由对应架构文档或 Spec 确定；Implementation Plan 只落实已经确认的设计，不能成为新增行为的另一处定义。

## Spec 与 Implementation Plan 的衔接

- Spec 的 2.6 验收标准承载行为测试方案及适用的效果评估方案；范围、确认条件、讨论阶段技术验证及联合验收规则见 [Spec 编写规范](spec-standard.md)。
- Plan 开头列出验收项与实施任务的对应关系，使用场景编号或明确链接引用。一个验收场景可以对应多个测试，不要求验收项、测试函数、任务或提交一一对应。
- Plan 不重复维护验收预期；逐任务安排测试文件、测试边界与数据、必要测试替身、生产代码改动和验证命令，并按需安排效果评估和 Git 提交。
- 任务只能实现已确认行为。普通实现细节在 TDD 中确定；遇到功能语义、契约或范围变化，先更新并确认对应设计，再同步验收场景和任务。
- 依赖后续 Spec 的联合验收应标明归属和当前状态，不用假实现或占位通过用例代替验证，也不以延期联合验收免除本任务的核心交付责任。

## Plan 内代码基底

写出代码前必须先对齐当前代码事实和项目基底规范。

### 当前代码事实

- 编写计划或代码前，应读取目标模块、相关测试、接口和数据定义，以及项目实际存在的配置与公共组件。新增模块尚无实现时，以已确认的 Spec 和当前项目结构为依据。
- 不得把尚不存在且未在计划中定义的类型、函数、文件、接口或存储组件当作可用依赖；计划中新建的依赖应明确先后关系。
- 不得发明与当前代码事实冲突的字段、错误模型、数据结构或命名。
- Plan 可以明确迁移或替换当前实现。只有发现未被 Plan 覆盖、并且会改变已确认设计、任务范围或公开 Contract 的冲突时，才停止并反馈。

### 复用既有基建

- 现有数据定义、接口、配置、日志、存储和边界校验组件与当前需求的语义和职责一致时，优先复用。
- 不重复实现已经存在且语义一致的解析器、错误模型、ID 规则或过滤逻辑，也不为了复用而继续沿用职责错误的抽象。
- 结构化数据变更应同步相关类型定义、实际使用的运行时校验和边界测试；不得仅为满足规范引入额外框架。

### 代码可读性与注释

- 新增的非自动生成代码文件应在文件开头用所用语言的文档机制简要说明职责、所属模块或主要协作对象；Python 模块使用 docstring，自动生成文件由生成器维护。
- 大幅修改既有代码文件时，如果文件缺少文件头说明，应顺手补齐；纯机械小改不要求为了注释扩大 diff。
- 注释默认使用英文。文档、测试名称、用户可见文案可以按项目语言规则使用中文。
- 新增或大幅修改的 Python 公开接口使用 docstring 说明职责与契约；其他语言使用相应的文档机制。非平凡内部函数应说明其职责。
- 名称和类型已经完整表达职责的简单内部辅助函数不要求机械添加注释；输入、输出、副作用、错误语义或关键约束不显然时必须说明。
- 复杂流程、跨模块边界、非显然约束、外部服务适配、数据迁移和兼容清理应说明设计理由；接口、数据校验及边界检查的关键文件应说明它们保护的长期边界。
- 注释解释意图、边界、不变量或取舍，不复述语法或变量名含义。不写 `Set value`、`Call function`、`Return result` 等无信息量注释。

### 可验证性与范围

- 对确定性的功能行为、业务规则和接口契约，采用 TDD；检索、排序和模型生成的质量按 Spec 中确认的效果评估方案验证，相关的输入校验、结果结构、约束处理和错误处理仍采用行为测试。
- 测试验证调用方或系统边界可观察的行为，不复述内部实现。新增或修改接口、数据校验、存储行为或模块边界规则时，应补充针对相关行为的测试；纯文档及不改变运行行为的机械调整，采用与变更相称的检查。
- Plan 内代码只能实现目标 Spec 和当前 Plan 范围，不顺手实现后续 Spec。

## 执行基底

- 对采用 TDD 的行为，执行 Plan 时逐条运行 Red → Green → Refactor：先写或替换对应测试，确认目标行为尚未实现导致失败，再完成最小实现使其通过，有实际收益时再重构。效果评估任务按 Spec 中确认的数据、指标和通过标准执行，不用模拟结果代替真实质量评估。
- 不先写完整批测试再集中实现全部功能；一个行为完成循环后，再处理下一行为。环境、依赖、语法等无关故障不能代替行为测试的 Red。
- 每个任务明确对应验收项、具体测试与生产代码改动、检查方式及完成条件；普通实现细节可在循环中确定，不要求提前写好全部生产代码。
- 已启用 Git 时，大功能、迁移和风险较高的重构使用独立分支或 worktree；提交粒度由 Implementation Plan 明确，不要求每个 task 单独提交。尚未启用 Git 时，应在实施准备中明确版本管理安排。
- 如果发现 Plan 未覆盖、并且会改变 target spec、已确认设计、任务范围或公开 Contract 的冲突，必须停下说明，不自行猜测。
- 为完成已确认行为所需、且不改变功能语义、公开契约或任务范围的配套文件调整，可同步更新 Plan 并在交付时说明。涉及上述设计变化时，应先说明影响并重新确认。

## 验证基底

Implementation Plan 应列出当前项目实际可执行的验证命令，并区分行为测试、集成验证和效果评估。依据变更范围执行已配置的静态检查、相关测试及文档检查；使用 Git 时执行 `git diff --check`。不得引用项目中不存在的脚本。

功能测试通过不等于效果评估通过；检索效果通过不等于最终修复效果通过。交付时分别记录验证结果及未验证的边界。打包和部署仅在本次交付范围包含时执行。

测试清理必须以当前行为和边界为依据：长期回归测试、接口与数据校验测试、存储行为测试，以及保护安全、隐私和架构边界的测试默认保留。阶段性迁移或清理测试只有在对应旧路径或旧组件明确废弃、并且当前模块已有等价覆盖时，才应删除或合并。

只改文档时通常不需要运行代码测试，但应检查改动差异及文档链接；如果文档会改变后续 Plan 或执行约束，应在交付说明中明确验证方式。

## 最终报告基底

执行计划的最终报告应包含完成结果、验证结果和偏离说明。有 Git 提交时列出相关提交；使用独立分支或 worktree 时说明对应名称；没有使用时不机械增加空报告项。
